One page, three places

Follow /courses from your browser to the database and back, then prove it with two console.logs.

≈ 20 minutes · You'll need a terminal open in the course repo (.. from this folder) · Reference: The request journey (cheat sheet)

Why this first

When Claude Code edits Cadence, every change lands in one of three places: the browser, the server or the database. If you can't tell which one, you can't judge whether a change makes sense. This lesson gives you that map, using one real page.

The three places

The client is your web browser. It can only show things and react to clicks. The server is a Node.js program running in your terminal (npm run dev). It is the only part allowed to read files and secrets. The database is a file, data.db, that stores tables of rows. Only the server talks to it.

The browser and server talk to each other over HTTP: When you click a link on a web page, submit a form, or run a search, the browser sends an HTTP Request to the server. The server works out an answer and sends back a response. (MDN)

② The loader: the server half of a route file

A route file can export a function called loader. React Router runs it on the server before showing the page. The docs say that the loader function is removed from client bundles so you can use server only APIs. (React Router docs)

③ → ④ The service talks to the database

Services in app/services/ are plain TypeScript functions that read and write data. They use Drizzle, a library that lets you write database queries as TypeScript. Drizzle turns this into SQL, the language SQLite understands:

app/services/courseService.ts · line 73 (simplified)db.select({ id: courses.id, title: courses.title, … })
  .from(courses)
  .innerJoin(users, eq(courses.instructorId, users.id))
  …
  .all();

For now, read it as English: "select these columns from the courses table, attach each course's instructor from the users table, and give me all the rows." A later lesson covers tables and joins properly.

⑤ The component: the part you see

The file's default export is a React component. React components are JavaScript functions that return markup. (react.dev) That markup is JSX, the HTML-like syntax inside .tsx files. The component never touches the database. Whatever the loader returned arrives as loaderData:

Check yourself

1. In CourseCatalog, where does the list of courses come from?

The loader runs on the server, gets the rows through the service and Drizzle, and returns them. React Router hands that return value to the component as loaderData. Components never talk to the database.

2. Which file describes the columns of the courses table?

schema.ts defines every table, e.g. sqliteTable("courses", { id, title, slug, price, … }). index.ts opens the connection to data.db, and routes.ts maps URLs to route files.

3. Why may the loader import database code when the component may not?

React Router strips the loader out of the code it sends to the browser, so server-only code such as database access is safe there. The component does get sent to the browser, as you'll prove below.

4. Which order matches a visit to /courses?

The request goes in through the route's loader, down through the service and Drizzle to SQLite, then the data comes back up and the component renders it.

Show what you should have seen (only after doing it)
  • LOADER ran only ever shows in the terminal, on a full reload and on sidebar navigation. On navigation the browser quietly asks the server to run the loader again (the docs call this an automatic fetch).
  • COMPONENT rendered on a full reload shows in both. The server renders the component once to build the first HTML, then the browser runs it again to make the page interactive. That second run is called hydration. On sidebar navigation it shows only in the browser.

So there are really three kinds of code: server only (loaders, services, db), browser only (click handlers and similar), and both (components). That third category is what trips people up, and a later lesson covers it.
